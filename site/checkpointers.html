LangGraph/核心能力/检查点保存器
核心能力

检查点保存器

LangGraph 检查点保存器会在每一步将图状态保存为检查点，从而支持持久化、人在回路和容错执行。

检查点保存器会在每个超步保存图状态的快照，并按线程组织。使用检查点保存器编译图，即可支持人在回路工作流、时间旅行调试、容错执行和对话记忆。

ℹ注意

Agent Server 会自动处理检查点 使用 Agent Server 时，你无需手动实现或配置检查点保存器。服务器会在后台为你处理所有持久化基础设施。

💡提示

使用 LangSmith 追踪已保存检查点的状态，并调试智能体如何跨会话恢复。按照追踪快速入门完成设置。

为什么使用检查点保存器#

以下功能需要使用检查点保存器：

  • 人在回路：检查点保存器通过允许人类检查、中断和批准图的步骤来支持人在回路工作流。这些工作流需要检查点保存器，因为用户必须能够查看图在任意时间点的状态，并且图必须能够在用户对状态做出任何更新后恢复执行。示例见中断。
  • 记忆：检查点保存器允许交互之间存在"记忆"。对于重复的人类交互（例如对话），任何后续消息都可以发送到该线程，线程会保留对先前消息的记忆。有关如何使用检查点保存器添加和管理对话记忆的信息，请参见添加记忆。
  • 时间旅行：检查点保存器允许"时间旅行"，使用户能够重放先前的图执行，以查看和/或调试特定的图步骤。此外，检查点保存器还能在任意检查点分叉图状态，以探索不同的轨迹。
  • 容错：检查点提供容错和错误恢复：如果一个或多个节点在给定超步失败，你可以从最后一个成功的步骤重新启动图。
  • 待处理写入：当某个图节点在给定超步执行中途失败时，LangGraph 会存储该超步中其他已成功完成的节点的待处理检查点写入。当你从该超步恢复图执行时，不会重新运行这些成功的节点。

核心概念#

线程#

线程是分配给检查点保存器所保存的每个检查点的唯一 ID 或线程标识符。它包含一系列运行的累积状态。当执行一次运行时，助手底层图的状态将被持久化到该线程。

使用检查点保存器调用图时，你必须在配置的 configurable 部分中指定 thread_id：

python
{"configurable": {"thread_id": "1"}}

线程的当前状态和历史状态都可以被检索。要持久化状态，必须在执行运行之前创建线程。LangSmith API 提供了多个用于创建和管理线程及线程状态的端点。详情请参见 API 参考。

检查点保存器使用 thread_id 作为存储和检索检查点的主键。没有它，检查点保存器就无法保存状态，也无法在中断后恢复执行，因为检查点保存器要使用 thread_id 来加载已保存的状态。

选择如何继续线程

thread_id 标识已保存的状态。输入和 checkpoint_id 决定一次调用是开始新的工作、恢复未完成的工作，还是重放历史。仅重用线程 ID 并不意味着执行会恢复。

在已有检查点保存器和已有线程的情况下，请根据你的目标选择调用方式：

目标调用方式执行行为
提交新输入graph.invoke(input, config)将输入应用到已保存状态，并从入口点开始执行。
在错误后继续graph.invoke(None, config)加载最新检查点并重试未完成的工作。省略 checkpoint_id。
回答 interrupt()graph.invoke(Command(resume=answer), config)提供中断的返回值。被中断的节点会从其开头重新开始。
重放历史graph.invoke(None, snapshot.config)使用来自 get_state_history() 的快照，并重新执行该检查点之后的节点。

新输入不会清空线程。LangGraph 会使用状态的归并函数来应用它。要使用空状态开始，请使用新的 thread_id。

当最新检查点没有未完成的工作时，恢复会返回已保存的结果而不运行节点。可运行的示例见Functional API 错误恢复、恢复中断和重放历史。

检查点#

线程在特定时间点的状态称为检查点。检查点是在每个超步保存的图状态快照，由 StateSnapshot 对象表示（完整字段参考见 StateSnapshot 字段）。

超步

LangGraph 会在每个超步边界创建一个检查点。超步是图的一次单独“tick”，在该步中被调度的所有节点都会执行（可能并行执行）。对于像 START -> A -> B -> END 这样的顺序图，输入、节点 A 和节点 B 分别有各自的超步——每完成一个就会产生一个检查点。理解超步边界对时间旅行很重要，因为你只能从检查点（即超步边界）恢复执行。

除了超步检查点之外，LangGraph 还会在节点（任务）级别持久化写入。当一个超步内的每个节点完成时，其输出会作为任务条目写入检查点保存器的 checkpoint_writes 表，并链接到进行中的检查点。正是这些按任务划分的写入实现了待处理写入恢复：如果同一超步中的另一个节点失败，成功节点的写入已经持久化，恢复时无需重新运行。随后，当超步完成时会提交完整的状态快照。

LangGraph 还会持久化超步内各个节点执行的写入。这些写入作为任务存储，并用于容错：如果同一超步中的另一个节点失败，恢复时无需重新计算成功节点的写入。这些任务写入不是完整的 StateSnapshot 检查点，因此时间旅行会从超步边界的完整检查点恢复。

检查点会被持久化，并可用于在之后恢复线程的状态。

让我们看看如下调用一个简单图时会保存哪些检查点：

python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.runnables import RunnableConfig
from typing import Annotated
from typing_extensions import TypedDict
from operator import add

class State(TypedDict):
    foo: str
    bar: Annotated[list[str], add]

def node_a(state: State):
    return {"foo": "a", "bar": ["a"]}

def node_b(state: State):
    return {"foo": "b", "bar": ["b"]}


workflow = StateGraph(State)
workflow.add_node(node_a)
workflow.add_node(node_b)
workflow.add_edge(START, "node_a")
workflow.add_edge("node_a", "node_b")
workflow.add_edge("node_b", END)

checkpointer = InMemorySaver()
graph = workflow.compile(checkpointer=checkpointer)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
graph.invoke({"foo": "", "bar":[]}, config)

运行该图后，将恰好有 4 个检查点：

  • 空检查点，下一个要执行的节点为 0
  • 包含用户输入 {'foo': '', 'bar': []} 的检查点，下一个要执行的节点为 node_a
  • 包含 node_a 输出 {'foo': 'a', 'bar': ['a']} 的检查点，下一个要执行的节点为 node_b
  • 包含 node_b 输出 {'foo': 'b', 'bar': ['a', 'b']} 的检查点，没有下一个要执行的节点

请注意，bar 通道的值包含两个节点的输出，因为本例为 bar 通道配置了归并函数。

检查点命名空间

每个检查点都有一个 checkpoint_ns（检查点命名空间）字段，用于标识它属于哪个图或子图：

  • ""（空字符串）：该检查点属于父（根）图。
  • "node_name:uuid"：该检查点属于作为给定节点调用的子图。对于嵌套子图，命名空间用 | 分隔符连接（例如 "outer_node:uuid|inner_node:uuid"）。

你可以通过 config 从节点内部访问检查点命名空间：

python
from langchain_core.runnables import RunnableConfig

def my_node(state: State, config: RunnableConfig):
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    # "" for the parent graph, "node_name:uuid" for a subgraph

有关使用子图状态和检查点的更多细节，请参见子图。

获取与更新状态#

获取状态#

与已保存的图状态交互时，你必须指定线程标识符。你可以通过调用 graph.get_state(config) 查看图的*最新*状态。该调用会返回一个 StateSnapshot 对象，它对应配置中提供的线程 ID 所关联的最新检查点；如果提供了检查点 ID，则对应线程中该检查点 ID 所关联的检查点。

python
# get the latest state snapshot
config = {"configurable": {"thread_id": "1"}}
graph.get_state(config)

# get a state snapshot for a specific checkpoint_id
config = {"configurable": {"thread_id": "1", "checkpoint_id": "1ef663ba-28fe-6528-8002-5a559208592c"}}
graph.get_state(config)

在此示例中，get_state 的输出如下所示：

获取状态历史#

你可以通过调用 0 获取给定线程的完整图执行历史。该调用会返回一个 StateSnapshot 对象列表，对应配置中提供的线程 ID。重要的是，检查点按时间先后排序，最新的检查点 / StateSnapshot 位于列表首位。

python
config = {"configurable": {"thread_id": "1"}}
list(graph.get_state_history(config))

查找特定检查点

你可以过滤状态历史，以查找符合特定条件的检查点：

python
history = list(graph.get_state_history(config))

# Find the checkpoint before a specific node executed
before_node_b = next(s for s in history if s.next == ("node_b",))

# Find a checkpoint by step number
step_2 = next(s for s in history if s.metadata["step"] == 2)

# Find checkpoints created by update_state
forks = [s for s in history if s.metadata["source"] == "update"]

# Find the checkpoint where an interrupt occurred
interrupted = next(
    s for s in history
    if s.tasks and any(t.interrupts for t in s.tasks)
)

列出所有线程

若要查看检查点保存器为哪些线程保存了状态（例如构建管理视图或调试视图），在列出检查点时省略 thread_id：

graph.get_state_history(config) 要求 config 中提供 thread_id，且只返回单个线程的历史。可在传给 compile 的同一个检查点保存器上调用 .list，并传入 config=None：

python
# config=None returns checkpoints across every thread
for checkpoint_tuple in checkpointer.list(None):
    print(checkpoint_tuple.config["configurable"]["thread_id"])

传入 None，而不是 {}。2 会将任何非 None 的配置视为线程过滤器，并在缺少 thread_id 时抛出错误。对于异步图，请改用 .alist(None)。此用法适用于 6、7 和 8。.list 仍然按每个检查点返回一行，而不是按线程返回，因此你需要自行按 thread_id 分组来构建线程列表。

重放#

重放会从先前的检查点重新执行步骤。用先前的 checkpoint_id 调用图，即可重新运行该检查点之后的节点。该检查点之前的节点会被跳过（其结果已保存）。该检查点之后的节点会重新执行，包括任何 LLM 调用、API 请求或中断——中断在重放期间总是会被重新触发。

有关重放历史执行的完整细节和代码示例，请参阅时间旅行。

更新状态#

你可以使用 0 编辑图状态。这会用更新后的值创建一个新的检查点——它不会修改原始检查点。该更新与节点更新的处理方式相同：当定义了归并函数时，值会通过归并函数传递，因此带归并函数的通道会*累积*值，而不是覆盖值。

你可以选择指定 as_node，以控制该更新被视为来自哪个节点，这会影响接下来执行哪个节点。详情请参阅时间旅行：1。

持久化模式#

LangGraph 支持三种持久化模式，让你可以在性能与数据一致性之间取得平衡。你可以在调用任意图执行方法时指定持久化模式：

python
graph.stream(
    {"input": "test"},
    durability="sync"
)

持久化模式按持久性从低到高排列如下：

  • "exit"：LangGraph 仅在图执行退出时持久化变更——无论是成功、出错，还是由于人在回路中断而退出。这为长时间运行的图提供了最佳性能，但意味着中间状态不会被保存，因此你无法在执行中途从系统故障（例如进程崩溃）中恢复。
  • "async"：LangGraph 在下一步执行期间异步持久化变更。这提供了良好的性能与持久性，但如果进程在执行期间崩溃，LangGraph 存在未写入检查点的小风险。
  • "sync"：LangGraph 在下一步开始前同步持久化变更。这确保 LangGraph 在继续执行前写入每一个检查点，以一定的性能开销为代价提供高持久性。

新线程上的首个持久化检查点#

对于新线程，持久化模式还决定了在第一个用户节点执行之前提交哪些检查点。内部的 __start__ 超步会先运行；步骤 0 是在该超步之后写入的循环检查点。

  • "exit"：在运行结束之前不存在任何检查点。运行期间崩溃不会留下该线程的任何记录。
  • "async"：LangGraph 会在第一个用户节点执行之前开始写入输入检查点，但不等待写入完成。第一个用户节点可能在任何一个检查点提交之前就已运行。
  • "sync"：LangGraph 会在第一个用户节点执行之前提交输入检查点（步骤 -1）和步骤 0 检查点。
⚠警告

在每种模式下，如果在第一个检查点变为持久化之前发生崩溃，该线程将与从未被调用过的线程无法区分：两种情况下的 get_tuple() 都返回 None，而 invoke(None, config) 会抛出 EmptyInputError。如果你需要区分“从未被接受”与“已接受但丢失”，请在检查点保存器之外记录受理信息，例如在调用 invoke 之前向自己的存储提交一条发件箱记录。

优化检查点存储#

默认情况下，LangGraph 检查点会在每个超步写入每个状态通道的完整值。对于累积量很大的长时间运行线程——例如多轮对话——这可能会随着时间推移导致存储量显著增长。

0 只存储增量差值，而不是完整的累积值，从而大幅减小追加密集型通道的检查点大小。用法以及存储与延迟之间的权衡请参见 DeltaChannel。

⚠警告

DeltaChannel 需要 langgraph>=1.2，目前处于 beta 阶段。该 API 在未来的版本中可能发生变化。

检查点库#

在底层，检查点由符合 0 接口的检查点对象驱动。LangGraph 提供了多种检查点实现，它们全部通过独立、可安装的库实现。

ℹ注意

有关可用的提供方，请参阅检查点集成。

  • langgraph-checkpoint：检查点保存器的基接口（1）以及序列化/反序列化接口（2）。包含用于实验的内存检查点实现（3）。LangGraph 自带 langgraph-checkpoint。
  • langgraph-checkpoint-sqlite：一种使用 SQLite 数据库的 LangGraph 检查点实现（1 / 2）。非常适合实验和本地工作流。需要单独安装。
  • langgraph-checkpoint-postgres：一种使用 Postgres 数据库的高级检查点（1 / 2），在 LangSmith 中使用。非常适合在生产环境中使用。需要单独安装。
  • langgraph-checkpoint-mongodb：一种使用 MongoDB 的高级检查点（MongoDBSaver / AsyncMongoDBSaver）。非常适合在生产环境中使用。需要单独安装。
  • langchain-azure-cosmosdb：一种使用 Azure Cosmos DB for NoSQL 的 LangGraph 检查点实现（1 / 2）。非常适合在 Azure 上用于生产环境。支持同步和异步操作，并支持 Microsoft Entra ID 身份验证。需要单独安装。

检查点接口#

每个检查点都符合 0 接口，并实现以下方法：

  • .put - 存储检查点及其配置和元数据。
  • .put_writes - 存储与检查点关联的中间写入（即待处理写入）。
  • .get_tuple - 根据给定配置（thread_id 和 checkpoint_id）获取检查点元组。用于在 graph.get_state() 中填充 StateSnapshot。
  • .list - 列出符合给定配置和筛选条件的检查点。用于在 graph.get_state_history() 中填充状态历史。传入 config=None 可列出所有线程中的检查点。请参阅列出每个线程。

如果检查点与异步图执行一起使用（即通过 .ainvoke、.astream、.abatch 执行图），则将使用上述方法的异步版本（.aput、.aput_writes、.aget_tuple、.alist）。

ℹ注意

如需异步运行图，可以使用 0，或 Sqlite/Postgres 检查点的异步版本 —— 1 / 2 检查点。

序列化器#

当检查点保存图状态时，它们需要序列化状态中的通道值。这通过序列化器对象完成。

langgraph_checkpoint 定义了用于实现序列化器的协议，并提供了默认实现（1），可处理多种类型，包括 LangChain 和 LangGraph 基础类型、日期时间、枚举等。

使用 pickle 进行序列化

默认序列化器 0 在底层使用 ormsgpack 和 JSON，这并不适用于所有类型的对象。

如果你希望为 msgpack 编码器目前不支持的对象的（例如 Pandas 数据帧）回退到 pickle， 可以使用 0 的 pickle_fallback 参数：

python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.serde.jsonplus import JsonPlusSerializer

# ... Define the graph ...
graph.compile(
    checkpointer=InMemorySaver(serde=JsonPlusSerializer(pickle_fallback=True))
)

加密

检查点可以选择加密所有持久化状态。要启用此功能，请将 0 的实例传给任意 1 实现的 serde 参数。创建加密序列化器最简单的方式是使用 3，它从 LANGGRAPH_AES_KEY 环境变量读取 AES 密钥（或接受 key 参数）：

python
import sqlite3

from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.sqlite import SqliteSaver

serde = EncryptedSerializer.from_pycryptodome_aes()  # reads LANGGRAPH_AES_KEY
checkpointer = SqliteSaver(sqlite3.connect("checkpoint.db"), serde=serde)
python
from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.postgres import PostgresSaver

serde = EncryptedSerializer.from_pycryptodome_aes()
checkpointer = PostgresSaver.from_conn_string("postgresql://...", serde=serde)
checkpointer.setup()

在 LangSmith 上运行时，只要存在 LANGGRAPH_AES_KEY，就会自动启用加密，因此你只需提供该环境变量。也可以实现 1 并将其提供给 2，以使用其他加密方案。

构建自定义检查点#

💡提示

在构建过程中，使用一致性测试套件验证你的实现。它覆盖全部五个基础方法以及包括增量通道在内的扩展能力。在发布前于 CI 中运行它。

本节介绍如何从零开始为自定义存储后端实现 BaseCheckpointSaver。如果你已有可用的检查点，只需要添加增量通道支持，请跳转到增量通道支持。

概述#

LangGraph 的持久化层构建在两个存储抽象之上：

  • 检查点表 —— 每个超步一行；存储序列化的图状态（channel_values、channel_versions、versions_seen），并链接到其父检查点。
  • 写入表 —— 每个超步内每个节点输出一行；存储链接到检查点的 (task_id, channel, value) 元组。

你的检查点管理器同时管理这两张表。put 写入一行检查点；put_writes 写入节点输出行；get_tuple 将二者读取回 CheckpointTuple。

基础契约#

继承 BaseCheckpointSaver 并实现这五个方法。它们全部是必需的——缺少基类方法会在运行时抛出 NotImplementedError。

python
from collections.abc import AsyncIterator, Iterator, Sequence
from typing import Any
from langchain_core.runnables import RunnableConfig
from langgraph.checkpoint.base import (
    BaseCheckpointSaver,
    ChannelVersions,
    Checkpoint,
    CheckpointMetadata,
    CheckpointTuple,
)

class MyCheckpointer(BaseCheckpointSaver):
    async def aput(
        self,
        config: RunnableConfig,
        checkpoint: Checkpoint,
        metadata: CheckpointMetadata,
        new_versions: ChannelVersions,
    ) -> RunnableConfig:
        ...

    async def aput_writes(
        self,
        config: RunnableConfig,
        writes: Sequence[tuple[str, Any]],
        task_id: str,
        task_path: str = "",
    ) -> None:
        ...

    async def aget_tuple(self, config: RunnableConfig) -> CheckpointTuple | None:
        ...

    async def alist(
        self,
        config: RunnableConfig | None,
        *,
        filter: dict[str, Any] | None = None,
        before: RunnableConfig | None = None,
        limit: int | None = None,
    ) -> AsyncIterator[CheckpointTuple]:
        ...
        yield  # make this an async generator

    async def adelete_thread(self, thread_id: str) -> None:
        ...

put / aput

存储一行检查点记录。返回带有已存储的 checkpoint_id 的更新后配置。

关键要求：

  • 使用 self.serde.dumps_typed(checkpoint) 序列化检查点——它会处理所有 LangGraph 原生类型，包括 delta 通道使用的 _DeltaSnapshot 数据块。
  • 完整存储 metadata——不要剥离未知的键。LangGraph 会在次要版本中新增元数据字段（例如 delta 通道的 counters_since_delta_snapshot），静默丢弃它们会破坏功能。
  • 将 config["configurable"].get("checkpoint_id") 存储为父检查点 ID，以便 get_tuple 能够填充 parent_config。
python
async def aput(self, config, checkpoint, metadata, new_versions):
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    checkpoint_id = checkpoint["id"]
    parent_id = config["configurable"].get("checkpoint_id")

    type_, blob = self.serde.dumps_typed(checkpoint)
    serialized_metadata = self.serde.dumps_typed(metadata)

    await self.db.execute(
        "INSERT INTO checkpoints (...) VALUES (...)",
        thread_id, checkpoint_ns, checkpoint_id, parent_id,
        type_, blob, *serialized_metadata,
    )
    return {
        "configurable": {
            "thread_id": thread_id,
            "checkpoint_ns": checkpoint_ns,
            "checkpoint_id": checkpoint_id,
        }
    }

put\_writes / aput\_writes

存储当前超步内单个任务的节点输出记录。这些记录通过 (thread_id, checkpoint_ns, checkpoint_id) 与检查点关联。

python
async def aput_writes(self, config, writes, task_id, task_path=""):
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    checkpoint_id = config["configurable"]["checkpoint_id"]

    rows = []
    for idx, (channel, value) in enumerate(writes):
        type_, blob = self.serde.dumps_typed(value)
        final_idx = WRITES_IDX_MAP.get(channel, idx)
        rows.append((thread_id, checkpoint_ns, checkpoint_id,
                      task_id, task_path, final_idx, channel, type_, blob))

    await self.db.executemany("INSERT INTO writes (...) VALUES (...)", rows)

从 langgraph.checkpoint.base 导入 WRITES_IDX_MAP。它把特殊通道（__error__、__interrupt__ 等）映射到保留的负索引，以免它们与常规写入索引冲突。

get\_tuple / aget\_tuple

检索一个检查点。配置中可能包含：

  • 没有 checkpoint_id——返回该线程 + 命名空间的最新检查点。
  • 指定 checkpoint_id——返回那个确切的检查点。

两条路径都必须正确工作。 指定 ID 的路径用于时间旅行，并且——至关重要地——用于每次图调用时的 delta 通道状态重建（参见 Delta 通道支持）。指定 ID 查找一旦失效，就会静默破坏 delta 通道状态。

python
async def aget_tuple(self, config):
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"].get("checkpoint_ns", "")
    checkpoint_id = config["configurable"].get("checkpoint_id")

    if checkpoint_id:
        row = await self.db.fetchone(
            "SELECT * FROM checkpoints "
            "WHERE thread_id=? AND checkpoint_ns=? AND checkpoint_id=?",
            thread_id, checkpoint_ns, checkpoint_id,
        )
    else:
        row = await self.db.fetchone(
            "SELECT * FROM checkpoints "
            "WHERE thread_id=? AND checkpoint_ns=? "
            "ORDER BY checkpoint_id DESC LIMIT 1",
            thread_id, checkpoint_ns,
        )

    if row is None:
        return None

    writes = await self.db.fetchall(
        "SELECT task_id, channel, type, value FROM writes "
        "WHERE thread_id=? AND checkpoint_ns=? AND checkpoint_id=? "
        "ORDER BY task_id, idx",
        thread_id, checkpoint_ns, row["checkpoint_id"],
    )
    pending_writes = [
        (w["task_id"], w["channel"], self.serde.loads_typed((w["type"], w["value"])))
        for w in writes
    ]

    checkpoint = self.serde.loads_typed((row["type"], row["blob"]))
    metadata = self.serde.loads_typed((row["metadata_type"], row["metadata"]))

    parent_config = None
    if row["parent_checkpoint_id"]:
        parent_config = {
            "configurable": {
                "thread_id": thread_id,
                "checkpoint_ns": checkpoint_ns,
                "checkpoint_id": row["parent_checkpoint_id"],
            }
        }

    return CheckpointTuple(
        config={
            "configurable": {
                "thread_id": thread_id,
                "checkpoint_ns": checkpoint_ns,
                "checkpoint_id": row["checkpoint_id"],
            }
        },
        checkpoint=checkpoint,
        metadata=metadata,
        parent_config=parent_config,
        pending_writes=pending_writes,
    )
⚠警告

行键 / 索引设计对指定 ID 查找至关重要。 如果你的存储使用按时间排序的键（例如反转的时间戳），而该键中没有嵌入 checkpoint_id，你就无法按 ID 直接读取行。你必须要么在行键中编码 checkpoint_id，要么构建二级索引。每次查找都做带值过滤的扫描虽然可行，但无法扩展。

list / alist

返回某个线程的检查点，最新的在前。遵守 before（只返回比该配置的 checkpoint_id 更早的检查点）和 limit。

delete\_thread / adelete\_thread

删除某个线程的所有检查点和写入。检查点记录行和写入记录行都必须删除。

行键 / 索引设计#

你存储和索引检查点的方式会直接影响正确性与性能。

推荐模式（SQL）：

sql
CREATE TABLE checkpoints (
    thread_id          TEXT NOT NULL,
    checkpoint_ns      TEXT NOT NULL DEFAULT '',
    checkpoint_id      TEXT NOT NULL,   -- ULID, lexicographically sortable newest-last
    parent_checkpoint_id TEXT,
    type               TEXT,
    checkpoint         BYTEA,
    metadata           JSONB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);

CREATE TABLE writes (
    thread_id     TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    task_id       TEXT NOT NULL,
    task_path     TEXT NOT NULL DEFAULT '',
    idx           INTEGER NOT NULL,
    channel       TEXT NOT NULL,
    type          TEXT,
    value         BYTEA,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, task_path, idx)
);

由于 checkpoint_id 是 ULID，它按字典序排序——值越大越新。"获取最新"就是 ORDER BY checkpoint_id DESC LIMIT 1；"按 ID 获取"就是在主键上做等值查找。

对于非 SQL 存储： 同样的原则适用。无论你采用哪种键方案，按 (thread_id, checkpoint_ns, checkpoint_id) 直接查找都必须是 O(1) 或接近 O(1)。避免那种按 ID 查找检查点的唯一方式是扫描某个线程所有行的设计。

序列化#

检查点、写入和元数据始终使用 self.serde（继承自 BaseCheckpointSaver，默认是 JsonPlusSerializer）。不要直接对元数据使用 pickle——它能工作，但 JsonPlusSerializer 产生人类可读的输出，并且版本处理更好。

JsonPlusSerializer 会自动处理所有 LangGraph 原生类型：

  • _DeltaSnapshot——delta 通道使用的哨兵数据块（msgpack 扩展码 7）
  • Pydantic v2 模型、dataclasses、numpy 数组、datetimes、枚举等

如果你编写自定义序列化器，请确保它能对 langgraph.checkpoint.serde.types 中的 _DeltaSnapshot 做往返转换。

扩展能力#

这些方法是可选的，但能解锁额外的 Agent Server 功能。如果你的存储后端能够高效支持它们，就实现它们。

方法它启用的能力
adelete_for_runs回滚多任务策略
acopy_thread高效的线程分叉
aprune线程历史修剪
aget_delta_channel_history高效的 delta 通道状态重建（见下文）

Agent Server 会在启动时自动检测你的检查点器实现了哪些能力，并激活相应的功能。

Delta 通道支持#

ℹ注意

DeltaChannel 处于 beta 阶段。 在设计稳定之前，API 与磁盘上的表示形式都可能发生变化。

DeltaChannel 是一种归并函数通道，它在检查点 blob 中只存储一个哨兵值（MISSING），而不是完整的通道值。状态通过归并函数重放祖先写入来重建。这使得对于像 messages 这类随时间不断累积的通道，每一步的检查点 blob 为 O(1)，而不是 O(N)。

运行时需要什么

当加载一个其 delta 通道不在 channel_values 中的检查点时，LangGraph 会调用 saver.get_delta_channel_history(config=config, channels=[...])。该调用会为每个通道返回：

  • writes —— 祖先链中对该通道的所有写入，按从旧到新的顺序排列，直到最近的快照为止。
  • seed（可选）—— 在最近的、拥有该值的祖先处存储的 _DeltaSnapshot blob；如果向上遍历到达根节点仍未找到快照，则该字段不存在。

然后运行时调用 channel.from_checkpoint(seed) 和 channel.replay_writes(writes) 来重建实时值。

默认实现

BaseCheckpointSaver 提供了一个默认的 get_delta_channel_history，它可与任何正确的 get_tuple 实现配合工作：

python
# Simplified from BaseCheckpointSaver
def get_delta_channel_history(self, *, config, channels):
    target = self.get_tuple(config)          # load the head checkpoint
    cursor = target.parent_config            # walk from its parent
    collected = {ch: [] for ch in channels}
    seed = {}
    remaining = set(channels)

    while cursor and remaining:
        tup = self.get_tuple(cursor)         # ← requires correct by-id lookup
        if tup is None:
            break
        for write in reversed(tup.pending_writes or []):
            if write[1] in remaining:
                collected[write[1]].append(write)
        for ch in list(remaining):
            if ch in tup.checkpoint["channel_values"]:
                seed[ch] = tup.checkpoint["channel_values"][ch]
                remaining.discard(ch)
        cursor = tup.parent_config

    return {
        ch: {"writes": list(reversed(collected[ch])), **({"seed": seed[ch]} if ch in seed else {})}
        for ch in channels
    }

关键依赖： get_tuple(cursor) 始终以特定的 checkpoint_id（父节点的 id）调用。如果该查询返回 None，遍历会立即停止，每个 delta 通道都会重建为空值——而且是在静默中发生，不会报错。这就是 get_tuple 中特定 id 路径必须正确的原因。

性能覆写

默认遍历会为每个祖先检查点发起一次 get_tuple 调用。对于查询支持良好的后端，可覆写 get_delta_channel_history（及其异步版本），用两次查询取回祖先链和写入：

python
async def aget_delta_channel_history(self, *, config, channels):
    if not channels:
        return {}

    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"].get("checkpoint_ns", "")
    checkpoint_id = config["configurable"]["checkpoint_id"]

    # Stage 1: stream ancestors newest-first until every channel has a seed
    ancestors = await self.db.fetchall(
        "SELECT checkpoint_id, parent_checkpoint_id, type, checkpoint "
        "FROM checkpoints "
        "WHERE thread_id=? AND checkpoint_ns=? AND checkpoint_id < ? "
        "ORDER BY checkpoint_id DESC",
        thread_id, checkpoint_ns, checkpoint_id,
    )

    chain_by_ch: dict[str, list[str]] = {ch: [] for ch in channels}
    seed_by_ch: dict[str, Any] = {}
    remaining = set(channels)
    cur_id = config["configurable"]["checkpoint_id"]

    for row in ancestors:
        if not remaining:
            break
        parent_id = row["parent_checkpoint_id"]
        ckpt = self.serde.loads_typed((row["type"], row["checkpoint"]))
        cv = ckpt.get("channel_values") or {}
        for ch in list(remaining):
            chain_by_ch[ch].append(row["checkpoint_id"])
            if ch in cv:
                seed_by_ch[ch] = cv[ch]
                remaining.discard(ch)
        cur_id = parent_id

    # Stage 2: fetch writes for each channel's ancestor chain in one query
    result: dict[str, DeltaChannelHistory] = {}
    for ch in channels:
        chain = chain_by_ch[ch]
        if not chain:
            entry: DeltaChannelHistory = {"writes": []}
            if ch in seed_by_ch:
                entry["seed"] = seed_by_ch[ch]
            result[ch] = entry
            continue

        write_rows = await self.db.fetchall(
            f"SELECT checkpoint_id, task_id, idx, type, value FROM writes "
            f"WHERE thread_id=? AND checkpoint_ns=? AND channel=? "
            f"AND checkpoint_id IN ({','.join('?' * len(chain))})"
            f"ORDER BY checkpoint_id, task_id, idx",
            thread_id, checkpoint_ns, ch, *chain,
        )
        writes_by_cid: dict[str, list[PendingWrite]] = {}
        for row in write_rows:
            cid = row["checkpoint_id"]
            value = self.serde.loads_typed((row["type"], row["value"]))
            writes_by_cid.setdefault(cid, []).append((row["task_id"], ch, value))

        # chain is newest-first; iterate oldest-first to get correct replay order
        collected: list[PendingWrite] = []
        for cid in reversed(chain):
            collected.extend(writes_by_cid.get(cid, []))

        entry = {"writes": collected}
        if ch in seed_by_ch:
            entry["seed"] = seed_by_ch[ch]
        result[ch] = entry

    return result

使用 delta 通道时进行剪枝

DeltaChannel 的状态并非自包含于单个检查点之中——它依赖于回溯到最近 _DeltaSnapshot 的祖先写入链。如果你实现 prune 或 delete_for_runs，则不能删除保留下来的检查点的 delta 通道所依赖的写入行。

安全选项：

  1. 剪枝前先遍历 —— 对每个打算保留的检查点，遍历其祖先链，并把直到最近 _DeltaSnapshot 的所有写入行标记为不可删除。
  2. 剪枝前强制快照 —— 在你保留的检查点上改写 channel_values[ch] = _DeltaSnapshot(reconstructed_value)，然后即可自由删除祖先。
  3. 对含 delta 通道的线程跳过剪枝 —— 如果你暂时不需要剪枝，这是最安全的短期选项。

使用 delta 通道复制线程

实现 copy_thread 时，要复制完整的祖先链——而不只是头检查点。目标线程必须拥有至少回溯到一个 _DeltaSnapshot 的写入行（对每个 delta 通道而言），否则这些通道在复制之后会重建为空值。
