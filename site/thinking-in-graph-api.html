使用 Graph API 构建

用 Graph API 思考

了解如何使用 LangGraph 的 Graph API，通过节点、边和共享状态来设计智能体。

当你使用Graph API 构建智能体时，你会把整个流程拆解为一个个称为节点的离散步骤。然后，你描述每个节点的判断与跳转逻辑。最后，你通过一个共享的状态把这些节点连接起来，每个节点都可以读取并写入该状态。

本演练使用 Graph API 构建一个客户支持邮件智能体。若要了解同一场景在 Functional API 中的实现，请参阅用 Functional API 思考。若要在两种 API 之间做出选择，请参阅在 Graph API 与 Functional API 之间选择。

从你想要自动化的流程开始#

设想你需要构建一个处理客户支持邮件的 AI 智能体。你的产品团队给出了以下需求：

txt
The agent should:

- Read incoming customer emails
- Classify them by urgency and topic
- Search relevant documentation to answer questions
- Draft appropriate responses
- Escalate complex issues to human agents

Example scenarios to handle:

1. Simple product question: "How do I reset my password?"
2. Bug report: "The export feature crashes when I select PDF format"
3. Urgent billing issue: "I was charged twice for my subscription!"
4. Feature request: "Can you add dark mode to the mobile app?"
5. Complex technical issue: "Our API integration fails intermittently with 504 errors"

要用 Graph API 实现一个智能体，本指南会向你展示五个步骤。步骤 1 和步骤 2 是规划阶段。步骤 3 到步骤 5 则把这份规划转化为状态、节点，以及一个可以运行的已编译图。

步骤 1：将工作流拆解为离散步骤#

首先找出流程中彼此独立的步骤。每个步骤都会成为一个节点（一个只做一件特定事情的函数）。然后勾勒出这些步骤之间的连接关系。请在编写代码之前完成这一步。

实线箭头是固定边：你在构建图时就声明它们，因为下一个节点在运行之前就已确定。虚线箭头是在节点内部、于运行时通过 0 选择的路径。

现在各组件已经识别出来，接下来明确每个节点需要做什么：

  • Read Email：提取并解析邮件内容
  • Classify Intent：使用 LLM 对紧急程度和主题进行分类，然后路由到搜索、缺陷跟踪或起草回复
  • Doc Search：在知识库中查询相关信息
  • Bug Track：在跟踪系统中创建或更新工单
  • Draft Reply：生成合适的回复，然后路由到人工审核或发送
  • Human Review：升级给人工坐席进行审批或处理
  • Send Reply：发送邮件回复
💡提示

有些节点始终沿固定边继续执行（Read Email 到 Classify Intent）。另一些节点则通过 Command 选择下一个节点（Classify Intent、Draft Reply、Human Review）。

步骤 2：确定每个步骤需要做什么#

对于步骤 1 中的每个节点，判断它属于哪类工作，以及需要哪些上下文。使用下面的分类，然后展开邮件智能体的示例，查看具体字段和重试选择。

LLM 步骤

当你需要理解、分析、生成文本或做出推理判断时使用

数据步骤

当你需要从外部来源检索信息时使用

操作步骤

当你需要执行外部操作时使用

用户输入步骤

当你需要人工介入时使用

LLM 步骤#

当某个步骤需要理解、分析、生成文本或做出推理判断时：

分类意图
  • 静态上下文（提示词）：分类类别、紧急程度定义、回复格式
  • 动态上下文（来自状态）：邮件内容、发件人信息
  • 期望结果：决定路由的结构化分类结果
起草回复
  • 静态上下文（提示词）：语气规范、公司政策、回复模板
  • 动态上下文（来自状态）：分类结果、搜索结果
  • 期望结果：可供审核的专业邮件回复

数据步骤#

当某个步骤需要从外部来源检索信息时：

文档搜索
  • 参数：根据意图和主题构建的查询
  • 重试策略：有，针对瞬时故障使用指数退避
  • 缓存：可以缓存常见查询以减少 API 调用

操作步骤#

当某个步骤需要执行外部操作时：

发送回复
  • 执行时机：审批之后（人工或自动）
  • 重试策略：有，针对网络问题使用指数退避
  • 不应缓存：每次发送都是唯一的操作
缺陷跟踪
  • 执行时机：只要意图为 "bug" 就执行
  • 重试策略：有，确保不丢失缺陷报告至关重要
  • 返回值：工单 ID，用于包含在回复中

用户输入步骤#

当某个步骤需要人工介入时：

人工审核
  • 决策上下文：原始邮件、回复草稿、紧急程度、分类结果
  • 期望输入格式：审批布尔值，以及可选的修改后回复
  • 触发时机：高紧急程度、账单问题或复杂问题
  • 被拒绝时：结束运行且不发送（由人工在图之外处理该邮件）

步骤 3：设计你的状态#

状态是智能体中所有节点都可访问的共享记忆。可以把它想象成智能体的笔记本，用来记录它在整个流程中了解到和决定的一切。

状态里应该放什么？#

针对每一份数据，问自己这些问题：

放入状态

它需要在多个步骤之间持久保留吗？如果需要，就放入状态。

不要存储

你能从其他数据推导出它吗？如果能，就在需要时计算，而不是存入状态。

对于邮件智能体，需要记录：

  • 原始邮件和发件人信息（之后无法重建）
  • 分类结果（后续节点需要）
  • 搜索结果或工单上下文（重新获取的代价较高）
  • 回复草稿（需要在审核过程中保留）
  • 执行元数据（用于调试和恢复）

保持状态原始，按需格式化提示词#

💡提示

在状态中存储原始数据，而不是格式化后的提示词文本。在节点内部需要时再格式化提示词。

这种分离意味着：

  • 不同节点可以用不同方式格式化同一份数据
  • 你可以修改提示词模板而不必改动状态模式
  • 调试时能看到每个节点实际收到的数据，而不是一个预先拼好的提示词字符串

现在定义状态。后续步骤中的节点会使用这些字段。

python
from typing import Literal, TypedDict


class EmailClassification(TypedDict):
    intent: Literal["question", "bug", "billing", "feature", "complex"]
    urgency: Literal["low", "medium", "high", "critical"]
    topic: str
    summary: str


class EmailAgentState(TypedDict):
    email_content: str
    sender_email: str
    email_id: str
    classification: EmailClassification | None
    search_results: list[str] | None  # Docs or ticket context
    draft_response: str | None

第 4 步：构建节点#

节点是一个 Python 函数，它接收当前状态并返回对状态的更新。当节点还要选择下一步时，返回 0。

妥善处理错误#

在填充节点主体之前，先想清楚每个节点可能如何失败。为调用外部 API 的节点附加重试策略。使用 interrupt() 获取人工输入。可以把下表当作指南：

错误类型由谁修复策略使用场景
瞬时错误（网络问题、速率限制）系统（自动）节点上的重试策略通常在重试后即可解决的临时失败
LLM 可恢复的错误（工具失败、解析问题）LLM将错误存入状态并路由回去模型可以借助更多上下文进行调整
用户可修复的错误（信息缺失、指令不清晰）人用 interrupt() 暂停需要用户输入才能继续
重试之后仍可恢复的失败开发者error_handler（Python）/ errorHandler（TypeScript）重试耗尽后运行补偿分支
意外错误开发者让运行失败需要修改代码才能修复的缺陷

关于重试策略、超时、补偿处理器、LLM 可恢复的循环、何时让错误向上冒泡，以及图级别的默认值，参见容错。

在本示例中，添加可能遇到瞬时失败的节点时，为其附加重试策略：

python
from langgraph.types import RetryPolicy

workflow.add_node(
    "search_documentation",
    search_documentation,
    retry_policy=RetryPolicy(max_attempts=3),
)

实现邮件智能体节点#

把每一项工作都变成一个节点。每个节点读取共享状态，完成一项工作，然后返回更新。当下一步取决于结果时，返回一个同时包含更新和目标位置的 Command。人工审核同样是一个节点：它在函数内部调用 interrupt()，而不是一个独立的图原语。

下面的桩代码展示了邮件智能体的函数签名、状态更新与路由。把占位的主体替换为真实的 LLM 调用和 API 集成。请把这些节点放在第 3 步的状态所在的同一个文件中。

在本演练中，read_email 是一个直通节点。即便如此，把它保留为独立节点仍然能让你在分类之前获得一个检查点，并为之后添加真正的 MIME 解析留出位置。

python
from typing import Literal

from langgraph.graph import END
from langgraph.types import Command, interrupt


def read_email(state: EmailAgentState) -> dict:
    """Parse and normalize the incoming email."""
    return {}


def classify_intent(
    state: EmailAgentState,
) -> Command[Literal["search_documentation", "bug_tracking", "draft_response"]]:
    """Classify intent and urgency, then route to gather context or draft."""
    # Placeholder: replace with a real LLM call.
    # This heuristic matches the try-out sample so interrupt() runs.
    lowered = state["email_content"].lower()
    if "charged" in lowered or "billing" in lowered:
        classification: EmailClassification = {
            "intent": "billing",
            "urgency": "high",
            "topic": "billing",
            "summary": "Customer reports a billing problem",
        }
    elif "crash" in lowered or "bug" in lowered:
        classification = {
            "intent": "bug",
            "urgency": "medium",
            "topic": "product bug",
            "summary": "Customer reports a bug",
        }
    else:
        classification = {
            "intent": "question",
            "urgency": "low",
            "topic": "general",
            "summary": "Customer question",
        }

    if classification["intent"] in ("question", "feature"):
        goto = "search_documentation"
    elif classification["intent"] == "bug":
        goto = "bug_tracking"
    else:
        goto = "draft_response"

    return Command(update={"classification": classification}, goto=goto)


def search_documentation(
    state: EmailAgentState,
) -> Command[Literal["draft_response"]]:
    """Search knowledge base for relevant information."""
    classification = state.get("classification") or {}
    topic = classification.get("topic", "general")
    return Command(
        update={"search_results": [f"Docs related to {topic}"]},
        goto="draft_response",
    )


def bug_tracking(state: EmailAgentState) -> Command[Literal["draft_response"]]:
    """Create or update a bug tracking ticket."""
    ticket_id = "BUG-12345"
    return Command(
        update={"search_results": [f"Bug ticket {ticket_id} created"]},
        goto="draft_response",
    )


def draft_response(
    state: EmailAgentState,
) -> Command[Literal["human_review", "send_reply"]]:
    """Draft a reply, then route to review or send."""
    classification = state.get("classification") or {}
    context = state.get("search_results") or []
    draft = f"Thanks for your email about {classification.get('topic', 'your request')}."
    if context:
        draft += f" Context: {context[0]}"

    needs_review = (
        classification.get("intent") in ("billing", "complex")
        or classification.get("urgency") in ("high", "critical")
    )
    goto = "human_review" if needs_review else "send_reply"
    return Command(update={"draft_response": draft}, goto=goto)


def human_review(
    state: EmailAgentState,
) -> Command[Literal["send_reply", END]]:
    """Pause for human review, then send or end."""
    classification = state.get("classification") or {}

    # Nodes re-run from the start on resume. Keep work before interrupt() idempotent.
    human_decision = interrupt(
        {
            "email_id": state.get("email_id", ""),
            "original_email": state.get("email_content", ""),
            "draft_response": state.get("draft_response", ""),
            "urgency": classification.get("urgency"),
            "intent": classification.get("intent"),
            "action": "Please review and approve/edit this response",
        }
    )

    if human_decision.get("approved"):
        return Command(
            update={
                "draft_response": human_decision.get(
                    "edited_response", state.get("draft_response", "")
                )
            },
            goto="send_reply",
        )
    # Rejection: human handles the email outside the graph
    return Command(update={}, goto=END)


def send_reply(state: EmailAgentState) -> dict:
    """Send the email response."""
    return {}

现在你已经有了节点函数。接下来，把它们接入一个已编译的图。

第 5 步：把它们连接起来#

把节点连接成一张图。由于路由逻辑位于 Command 节点内部，你只需要少量固定边。使用检查点保存器进行编译，这是 interrupt() 能够暂停和恢复的前提。

python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import RetryPolicy

workflow = StateGraph(EmailAgentState)

workflow.add_node("read_email", read_email)
workflow.add_node("classify_intent", classify_intent)
workflow.add_node(
    "search_documentation",
    search_documentation,
    retry_policy=RetryPolicy(max_attempts=3),
)
workflow.add_node(
    "bug_tracking",
    bug_tracking,
    retry_policy=RetryPolicy(max_attempts=3),
)
workflow.add_node("draft_response", draft_response)
workflow.add_node("human_review", human_review)
workflow.add_node("send_reply", send_reply)

workflow.add_edge(START, "read_email")
workflow.add_edge("read_email", "classify_intent")
workflow.add_edge("send_reply", END)

checkpointer = InMemorySaver()
app = workflow.compile(checkpointer=checkpointer)

返回 Command[Literal[...]] 的 Python 节点会在类型提示中声明其目标节点。LangGraph 据此得知哪些边是有效的。

试用你的智能体#

图编译完成后，用一封示例邮件调用它。使用上面的占位分类器时，这封紧急的账单邮件会被判定为高紧急度，因此本次运行会起草回复、触发 interrupt()，你可以借此练习恢复。首次调用和恢复调用要使用同一个 thread_id。

python
from langgraph.types import Command

config = {"configurable": {"thread_id": "customer_123"}}

result = app.invoke(
    {
        "email_content": "I was charged twice for my subscription! This is urgent!",
        "sender_email": "customer@example.com",
        "email_id": "email_123",
    },
    config,
)
# The graph pauses at human_review when urgency is high

app.invoke(
    Command(
        resume={
            "approved": True,
            "edited_response": "We sincerely apologize for the double charge. I've initiated an immediate refund...",
        }
    ),
    config,
)

图在 interrupt() 处暂停，将状态保存到检查点保存器并等待。当你用 Command(resume=...) 恢复时，human_review 节点会从头重新运行，interrupt() 返回你的恢复值，图继续执行。thread_id 把这轮对话的状态维系在一起。

总结与下一步#

关键要点#

构建这个邮件智能体的过程，展示了 Graph API 的思考方式：

拆分为离散的步骤

每个节点只把一件事做好。节点边界正是图执行检查点的位置，因此失败与恢复时重复的工作更少。

状态即共享内存

存储原始数据，而不是格式化后的文本。不同节点可以以不同方式使用同一份信息。

节点即函数

它们接收状态、执行工作，并返回更新。当它们进行路由时，会通过 Command 同时返回更新和下一个目的地。

错误是流程的一部分

瞬时失败会应用节点重试策略，用户可修复的问题通过 interrupt() 暂停，意料之外的错误则会让本次运行失败。

人类输入是一等公民

interrupt() 会暂停执行并保存状态。恢复时，节点会从头重新运行，因此请让 interrupt() 之前的工作保持幂等。

图结构保持精简

你只需声明必要的边。需要动态路由的节点会返回 Command，这让控制流保持显式且可追踪。

节点粒度的取舍#

大多数应用都可以采用上面的拆分方式。当你正在决定要合并还是拆分节点时，请阅读本节。

LangGraph 在节点边界处创建检查点。当运行在中断或失败之后恢复时，它会从执行停止所在节点的开头重新开始。节点越小，检查点越频繁，需要重复的工作也越少。

为什么这种拆分方式适合该邮件智能体：

  • 外部服务的隔离： Doc Search 和 Bug Track 是独立节点，因此重试只作用于这些 API 调用。
  • 可见性： 分类是它自己的节点，因此你可以在执行下一步操作之前检查结构化结果。
  • 不同的失败模式： LLM 调用、查询和邮件发送采用不同的重试策略。
  • 测试： 较小的节点更容易进行单元测试和复用。

把 Read Email 和 Classify Intent 合并为一个节点是可行的。这样你会失去它们之间的一个检查点，并在失败时重复两者的工作。对大多数智能体而言，独立节点带来的可观测性收益是值得的。

缓存搜索结果属于节点函数内部的应用层选择。LangGraph 并不为此规定缓存 API。节点更多并不一定意味着运行更慢：默认情况下，检查点在后台写入（异步持久化模式）。
