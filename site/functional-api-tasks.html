使用 Functional API 构建

配置 Functional API 任务

为 Functional API 的任务和入口点添加重试、超时、缓存和错误恢复。

任务是一个独立的工作单元，其结果可以被单独检查点保存。当入口点或 Graph API 节点执行多个操作时，应把每个操作都包裹在任务中，而不是把所有工作都放在一个函数体里。配合检查点保存器，已完成的任务结果会被保存，因此恢复的线程可以跳过已完成的工作，从下一个任务继续。

本页介绍任务的重试、超时、缓存和错误恢复。概念部分请参阅 Functional API 概览。按顺序的构建路径请参阅 Functional API 构建清单。共享的重试与超时生命周期请参阅容错。

添加重试策略#

在 @task 上传入 retry_policy。默认的 RetryPolicy 会对选定的网络错误和 HTTP 5xx 错误进行重试，但不会重试 ValueError。本示例对 ValueError 进行重试。

python
from langgraph.func import entrypoint, task
from langgraph.types import RetryPolicy

# Used only to simulate a transient failure. Do not use a global like this in production.
attempts = 0

retry_policy = RetryPolicy(retry_on=ValueError)


@task(retry_policy=retry_policy)
def get_info():
    global attempts
    attempts += 1

    if attempts < 2:
        raise ValueError("Failure")
    return "OK"


@entrypoint()
def main(inputs):
    return get_info().result()


print(main.invoke({"any_input": "foobar"}))
# 'OK'

设置超时#

限制单次异步尝试可以运行多长时间。如果重试策略会重试该超时错误，则计时器在下一次尝试时重置。

在 @task 或 @entrypoint 上以秒为单位或使用 datetime.timedelta 传入 timeout。超时仅适用于异步任务和入口点。在同步函数上设置 timeout 会在声明时引发错误。

第一次尝试的休眠时间超过了超时限制，并引发 0，它是 TimeoutError 的子类。重试策略会重试该错误。第二次尝试立即返回。

python
import asyncio

from langgraph.errors import NodeTimeoutError
from langgraph.func import entrypoint, task
from langgraph.types import RetryPolicy

attempts = 0


@task(
    timeout=1.0,
    retry_policy=RetryPolicy(retry_on=NodeTimeoutError),
)
async def call_api(url: str) -> str:
    global attempts
    attempts += 1
    if attempts < 2:
        await asyncio.sleep(2)
    return f"result from {url}"


@entrypoint(timeout=5.0)
async def workflow(inputs: dict) -> str:
    return await call_api(inputs["url"])


print(asyncio.run(workflow.ainvoke({"url": "https://example.com"})))
# 'result from https://example.com'

缓存任务#

按输入缓存任务结果。在入口点上传入缓存，在任务上传入策略。ttl 以秒为单位。第二次调用命中缓存，因此本次运行大约耗时 1 秒，而不是 2 秒。

python
import time

from langgraph.cache.memory import InMemoryCache
from langgraph.func import entrypoint, task
from langgraph.types import CachePolicy


@task(cache_policy=CachePolicy(ttl=120))
def slow_add(x: int) -> int:
    time.sleep(1)
    return x * 2


@entrypoint(cache=InMemoryCache())
def main(inputs: dict) -> dict[str, int]:
    result1 = slow_add(inputs["x"]).result()
    result2 = slow_add(inputs["x"]).result()
    return {"result1": result1, "result2": result2}


print(main.invoke({"x": 5}))
# {'result1': 10, 'result2': 10}

出错后恢复#

需要检查点保存器，以便已完成的任务结果能在运行失败后保留下来。

恢复会从入口点的开头开始。LangGraph 会从检查点恢复已完成 slow_task 的结果，因此其函数体不会再次运行。失败的 get_info 任务会再次运行并返回 "OK"。下面的执行日志区分了入口点的重新进入与任务的重新执行。

用 None 恢复同一个 thread_id。

python
import time

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task

# Used only to simulate a transient failure. Do not use a global like this in production.
attempts = 0
called: list[str] = []


@task()
def get_info():
    global attempts
    called.append("get_info")
    attempts += 1

    if attempts < 2:
        raise ValueError("Failure")
    return "OK"


checkpointer = InMemorySaver()


@task
def slow_task():
    called.append("slow_task")
    time.sleep(1)
    return "Ran slow task."


@entrypoint(checkpointer=checkpointer)
def main(inputs):
    called.append("entrypoint")
    slow_task_result = slow_task().result()
    get_info().result()  # raises ValueError on the first run
    return slow_task_result


config = {"configurable": {"thread_id": "1"}}

try:
    main.invoke({"any_input": "foobar"}, config=config)
except ValueError:
    pass

assert called == ["entrypoint", "slow_task", "get_info"]
called.clear()

print(main.invoke(None, config=config))
# 'Ran slow task.'
assert called == ["entrypoint", "get_info"]
print(called)
# ['entrypoint', 'get_info']

再次传入原始输入会启动一次新的调用，而不是恢复失败的那次调用。请参阅选择如何继续线程。

恢复会还原已完成任务的结果，但不会选择性地重新运行某个已完成的任务。Functional API 的任务结果共享入口点的检查点，而不是在每个任务之前创建完整的检查点。若要从图中特定的步骤回放，请使用 Graph API 的时间旅行。
