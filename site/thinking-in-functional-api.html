使用 Functional API 构建

使用 Functional API 进行思考

学习如何使用入口点、任务和普通控制流，通过 LangGraph Functional API 设计智能体。

当你使用Functional API 构建智能体时，你会把流程拆分为称为任务的离散工作单元。你在入口点内使用普通的语言控制流（if/else、循环和函数调用）组合这些任务。值以返回值的形式在任务之间传递，而不是通过共享的图状态模式。

本演练使用 Functional API 构建一个客户支持邮件智能体。如需了解使用 Graph API 实现同一场景，请参阅使用 Graph API 进行思考。如需在两种 API 之间做选择，请参阅在 Graph API 与 Functional API 之间选择。

从你想要自动化的流程开始#

假设你需要构建一个处理客户支持邮件的 AI 智能体。你的产品团队给出了以下需求：

txt
The agent should:

- Read incoming customer emails
- Classify them by urgency and topic
- Search relevant documentation to answer questions
- Draft appropriate responses
- Escalate complex issues to human agents

Example scenarios to handle:

1. Simple product question: "How do I reset my password?"
2. Bug report: "The export feature crashes when I select PDF format"
3. Urgent billing issue: "I was charged twice for my subscription!"
4. Feature request: "Can you add dark mode to the mobile app?"
5. Complex technical issue: "Our API integration fails intermittently with 504 errors"

要使用 Functional API 实现智能体，请遵循以下五个步骤。步骤 1 和步骤 2 是规划。步骤 3 到步骤 5 将这份计划转化为可运行的类型、任务和入口点。

步骤 1：将工作流拆解为离散步骤#

首先识别流程中各个不同的步骤。每个步骤都会成为一个任务（执行某一特定功能的函数）。然后勾勒出入口点如何调用这些任务以及如何分支。在编写代码之前完成这一步。

该草图与入口点相对应：左侧是顺序调用和 if/else，右侧是人工审核。Graph API 会将相同的路径编码为节点和边。

现在组件已经确定，请明确每个步骤需要做什么：

  • Read Email：提取并解析邮件内容
  • Classify Intent：使用 LLM 对紧急程度和主题进行分类
  • Doc Search：查询知识库以获取相关信息
  • Bug Track：在跟踪系统中创建或更新 issue
  • Draft Reply：生成合适的回复
  • Human Review：升级给人工客服进行审批或处理
  • Send Reply：发送邮件回复
💡提示

有些步骤总是按顺序执行（Read Email 然后 Classify Intent）。其他步骤则是有条件的（Doc Search 用于问题和功能请求，Bug Track 仅用于缺陷）。在入口点中使用普通控制流来编码这些分支。

步骤 2：确定每个步骤需要做什么#

对于步骤 1 中的每个步骤，判断它属于哪类工作以及需要哪些输入。使用下面的分类，然后展开邮件智能体示例以了解具体字段和重试选择。

LLM 步骤

当你需要理解、分析、生成文本或做出推理决策时使用

数据步骤

当你需要从外部来源检索信息时使用

操作步骤

当你需要执行外部操作时使用

用户输入步骤

当你需要人工介入时使用

LLM 步骤#

当一个步骤需要理解、分析、生成文本或做出推理决策时：

分类意图
  • 静态上下文（提示词）：分类类别、紧急程度定义、响应格式
  • 动态上下文（参数）：邮件内容、发件人信息
  • 期望结果：驱动后续分支的结构化分类
起草回复
  • 静态上下文（提示词）：语气指南、公司政策、回复模板
  • 动态上下文（参数）：分类结果、搜索结果
  • 期望结果：可供审核的专业邮件回复

数据步骤#

当一个步骤需要从外部来源检索信息时：

文档搜索
  • 参数：根据意图和主题构建的查询
  • 重试策略：是，对暂时性故障采用指数退避
  • 缓存：可以缓存常见查询以减少 API 调用

操作步骤#

当一个步骤需要执行外部操作时：

发送回复
  • 执行时机：审批之后（人工或自动）
  • 重试策略：是，针对网络问题采用指数退避
  • 不应缓存：每次发送都是唯一的操作
缺陷跟踪
  • 执行时机：当意图为 "bug" 时总是执行
  • 重试策略：是，不丢失缺陷报告至关重要
  • 返回：要包含在回复中的工单 ID

用户输入步骤#

当一个步骤需要人工介入时：

人工审核
  • 决策所需上下文：原始邮件、草稿回复、紧急程度、分类
  • 预期输入格式：审批布尔值加上可选的编辑后回复
  • 触发时机：高紧急程度、复杂问题或质量疑虑

步骤 3：决定任务之间传递哪些数据#

在 Functional API 中，没有共享的图状态模式。每个任务接收参数并返回一个值。入口点将中间结果保存在局部变量中，并传递给下一个任务。

针对每一份数据，问自己以下问题：

在任务之间共享

后续任务是否需要这个值？如果需要，从创建它的任务中返回该值，将其存储在入口点的局部变量中，然后作为参数传递给需要它的任务。

保留在单个任务内部

它是否只用于在一个任务内部格式化提示词或发起调用？如果是，请将其保留在该任务本地。不要返回它。

对于邮件智能体，入口点需要携带：

  • 原始邮件和发件人信息（工作流的输入）
  • 分类结果（后续分支和起草步骤需要）
  • 搜索结果（重新获取成本高）
  • 草稿回复（审核和发送过程需要）
💡提示

存储并传递原始数据，而不是格式化后的提示词文本。在调用模型的任务内部格式化提示词。这样可以保持任务可复用，并使检查点更容易检查。

为任务之间交换的值定义类型。这些是普通的 TypedDict 或 TypeScript 类型，而不是 Graph API 的状态模式。现在就将它们添加到你的文件中；后续步骤中的任务和入口点会用到它们。

python
from typing import Literal, TypedDict


class EmailClassification(TypedDict):
    intent: Literal["question", "bug", "billing", "feature", "complex"]
    urgency: Literal["low", "medium", "high", "critical"]
    topic: str
    summary: str


class EmailInput(TypedDict):
    email_content: str
    sender_email: str

步骤 4：构建你的任务#

把步骤 1 中的每个工作单元变成一个任务。任务会独立地写入检查点、在失败时重试，并返回入口点可以等待的值。

0 是一个 Python 函数，它完成一个工作单元并返回结果。在入口点中调用它，并用 .result() 解析结果（或在异步入口点中 await）。

恰当地处理错误#

在填写任务主体之前，先考虑每个任务可能如何失败。为瞬时错误在任务上附加重试。在入口点中使用 interrupt() 获取人工输入。以下表作为指引：

错误类型由谁修复策略何时使用
瞬时错误（网络问题、速率限制）系统（自动）任务上的重试策略通常在重试后即可解决的临时失败
LLM 可恢复的错误（工具失败、解析问题）LLM返回错误，并在入口点中分支或重试模型可以借助更多上下文自行调整
用户可修复的错误（信息缺失、指令不清）人用 interrupt() 暂停需要用户输入才能继续
意外错误开发者让本次运行失败需要修复代码的 bug

实现邮件智能体任务#

为步骤 1 中的每个步骤添加一个任务（人工审核除外，它在步骤 5 中通过入口点里的 interrupt() 实现）。下面的桩函数展示了邮件智能体的函数签名、返回结构和重试策略。用真实的 LLM 调用和 API 集成替换占位的函数体。把这些任务与步骤 3 中的类型放在同一个文件里。

这里的 read_email 是一个透传任务。即便如此，把它保留为独立任务仍能在分类之前获得一个检查点，并留出一个后续添加真实 MIME 解析的位置。

python
from langgraph.func import task
from langgraph.types import RetryPolicy


@task
def read_email(email_content: str, sender_email: str) -> dict:
    """Parse and normalize the incoming email."""
    return {
        "email_content": email_content,
        "sender_email": sender_email,
    }


@task
def classify_intent(email_content: str, sender_email: str) -> EmailClassification:
    """Classify intent and urgency with an LLM."""
    # Placeholder: replace with a real LLM call.
    # This heuristic matches the try-out sample so interrupt() runs.
    lowered = email_content.lower()
    if "charged" in lowered or "billing" in lowered:
        return {
            "intent": "billing",
            "urgency": "high",
            "topic": "billing",
            "summary": "Customer reports a billing problem",
        }
    if "crash" in lowered or "bug" in lowered:
        return {
            "intent": "bug",
            "urgency": "medium",
            "topic": "product bug",
            "summary": "Customer reports a bug",
        }
    return {
        "intent": "question",
        "urgency": "low",
        "topic": "general",
        "summary": "Customer question",
    }


@task(retry_policy=RetryPolicy(max_attempts=3))
def search_documentation(topic: str, summary: str) -> list[str]:
    """Query the knowledge base for relevant chunks."""
    return [f"Docs related to {topic}"]


@task(retry_policy=RetryPolicy(max_attempts=3))
def create_bug_ticket(
    email_content: str, sender_email: str, summary: str
) -> str:
    """Create a ticket and return its ID."""
    return "TICKET-123"


@task
def draft_response(
    email_content: str,
    classification: EmailClassification,
    context: list[str],
) -> str:
    """Draft a reply from the email, classification, and gathered context."""
    return f"Thanks for your email about {classification['topic']}."


@task
def send_reply(draft: str, sender_email: str) -> None:
    """Send the approved reply."""
    return None

现在你有了可调用的任务。接下来，在入口点中把它们组合起来。

步骤 5：组合入口点#

入口点就是工作流。把它添加在任务下方。它会按顺序调用这些任务，用 if/else 进行分支（即步骤 1 中的控制流），并用 interrupt() 为人工暂停。当你需要持久执行和人在回路时，请提供检查点保存器。

python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint
from langgraph.types import interrupt

checkpointer = InMemorySaver()


@entrypoint(checkpointer=checkpointer)
def email_agent(inputs: EmailInput) -> dict:
    parsed = read_email(inputs["email_content"], inputs["sender_email"]).result()
    classification = classify_intent(
        parsed["email_content"], parsed["sender_email"]
    ).result()

    context: list[str] = []
    if classification["intent"] in ("question", "feature"):
        context = search_documentation(
            classification["topic"], classification["summary"]
        ).result()
    elif classification["intent"] == "bug":
        ticket_id = create_bug_ticket(
            parsed["email_content"],
            parsed["sender_email"],
            classification["summary"],
        ).result()
        context = [f"Ticket created: {ticket_id}"]

    draft = draft_response(
        parsed["email_content"], classification, context
    ).result()

    # Pause for human review on billing, urgent, or complex issues
    if (
        classification["intent"] in ("billing", "complex")
        or classification["urgency"] in ("high", "critical")
    ):
        human_decision = interrupt(
            {
                "email_content": parsed["email_content"],
                "draft_response": draft,
                "classification": classification,
            }
        )
        if not human_decision.get("approved"):
            return {"status": "escalated", "draft": draft}
        draft = human_decision.get("edited_response", draft)

    send_reply(draft, parsed["sender_email"]).result()
    return {"status": "sent", "draft": draft, "classification": classification}

试用你的智能体#

入口点定义好之后，用一封示例邮件调用它。使用上面占位版的分类器时，这封紧急的账单邮件会被判定为高紧急程度，因此本次运行会命中 interrupt()，你可以练习恢复。首次调用和恢复调用要使用相同的 thread_id。

python
from langgraph.types import Command

config = {"configurable": {"thread_id": "customer_123"}}

result = email_agent.invoke(
    {
        "email_content": "I was charged twice for my subscription! This is urgent!",
        "sender_email": "customer@example.com",
    },
    config,
)
# The workflow pauses at interrupt() when urgency is high

# Resume with the human decision
email_agent.invoke(
    Command(
        resume={
            "approved": True,
            "edited_response": "We sincerely apologize for the double charge. I've initiated an immediate refund...",
        }
    ),
    config,
)

工作流在 interrupt() 处暂停，把已完成任务的结果保存到检查点保存器，然后等待。当你用 Command(resume=...) 恢复时，已完成的任务会从检查点重新加载，而不是重新运行。thread_id 把这轮对话的状态维系在一起。

总结与后续步骤#

关键要点#

构建这个邮件智能体展示了 Functional API 的思维方式：

拆分为独立的任务

每个任务只做好一件事。任务边界是结果写入检查点的地方，因此失败和恢复时需要重做的工作更少。

传递值，而不是共享图状态

从任务返回原始数据，并将其作为参数传递。把提示词格式化留在需要它的任务内部。

入口点掌控控制流

使用 if/else、循环和调用。你无需声明边或条件边映射。

错误是流程的一部分

瞬时故障交给任务重试策略，用户可修复的问题通过 interrupt() 暂停，意外错误则使本次运行失败。

人类输入是一等公民

interrupt() 会暂停执行、保存已完成任务的结果，并在你提供输入后恢复。

组合仍留在代码中

工作流读起来就像普通函数。这契合既有的过程式代码和快速迭代。

任务粒度的权衡#

大多数应用都可以采用上述拆分方式。当你需要决定合并还是拆分任务时，请阅读本节。

LangGraph 会在入口点内部的 任务 边界处设置检查点。当一次运行在中断或失败后恢复时，已完成任务的结果会从检查点加载。位于任务之外、直接写在入口点主体中的工作可能会重新执行。

为什么这种拆分适合这个邮件智能体：

  • 隔离外部服务： 文档搜索和缺陷跟踪是各自独立的任务，因此重试和失败都被限制在这些 API 调用范围内。
  • 可见性： 分类是独立任务，因此你可以在分支之前检查结构化结果。
  • 不同的失败模式： LLM 调用、数据库查询和邮件发送采用不同的重试策略。
  • 测试： 更小的任务更容易做单元测试和复用。

将 read_email 和 classify_intent 合并为一个任务也是可行的。但你会失去两者之间的检查点，失败时需要重复执行这两个任务。对大多数智能体而言，拆分任务带来的可观测性收益是值得的。
