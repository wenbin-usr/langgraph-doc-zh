部署

向后兼容

在生产环境中更新 LangGraph 图代码，同时不破坏在途运行。

软件在生产环境中需要不断变更。新需求、缺陷修复和重构最终都会落到你的图代码中。由于 LangGraph 会用最新部署的图去运行已有线程中持久化的状态，你发布的每一次变更，实际上都是针对已有检查点的一次向后兼容的 API 变更。

有些工作流引擎会把一次运行固定在其启动时所使用的代码版本上，LangGraph 则不同：它会立即把最新的图应用到*每一个*线程，无论是新线程还是从检查点恢复的线程。这很方便：缺陷修复无需额外操作即可传递到在途的对话和智能体。但这也意味着，你必须推敲每项变更会如何与在旧版本代码下启动的运行相互作用。

需要留意的兼容性问题大致有三类，下面按你通常会遇到的先后顺序排列：

  1. 技术兼容性：最常见；新代码必须仍能针对已有的状态加载和执行。
  2. 业务兼容性：较少见；已有运行应当继续遵循旧的业务逻辑，即使代码已经改变。
  3. 非确定性：仅适用于Functional API。
💡提示

关于运行时默认支持哪些图拓扑和状态变更的简要说明，请参见图迁移。本页其余部分介绍的是当变更超出该支持范围时可以采用的模式。

技术兼容性#

技术兼容性相当于微服务中的 API 破坏性变更。这里的“API”指的是你的图代码与检查点保存器为已有线程已持久化的数据之间的约定。当线程恢复时，LangGraph 会反序列化已保存的状态，按名称将其分派给某个节点，并期望该节点返回符合状态模式的值。

常见的技术性破坏：

  • 重命名或删除节点，而线程正暂停在该节点处或即将进入该节点，例如停在某个 0 处，或经由一条已被检查点记录、仍路由到旧名称的条件边。恢复时，LangGraph 无法按其保存的名称找到该节点，运行就会失败。恢复运行的起点是执行停止所在节点的开头，因此节点缺失就无处可恢复。
  • 重命名或删除状态键，而较旧的检查点仍包含该键，或下游节点仍在读取该键。
  • 收紧状态字段，例如把 Optional 字段改为必填、收窄类型，或新增一个没有默认值的必填字段。已有的检查点将无法满足新的模式。

边拓扑本身*不会*持久化到检查点中。在仍然存在的节点之间新增、删除或重定向边，对在途线程是安全的。按照图迁移一节的总结，唯一可能破坏已中断线程的拓扑变更就是重命名或删除节点。

推荐模式#

  • 把新增的状态字段声明为 NotRequired（或 Optional[...] = None），这样旧的检查点仍能通过校验：
    python
    from typing import NotRequired
from typing_extensions import TypedDict

class State(TypedDict):
    messages: list
    summary: NotRequired[str]
  • 把删除当作弃用处理。即使没有节点读取该字段，也要在状态上至少保留一个排空周期，以便已有的检查点继续加载。
  • 通过*先加后删*来完成重命名。在旧字段或旧节点旁边新增新的字段或节点，在弃用窗口内双写或同时路由到两者，待确认没有任何在途线程依赖旧字段或旧节点后，再将其删除。
  • 让节点函数能够容忍未知的键。TypedDict 在运行时忽略多余的键，因此旧代码版本遗留的状态不会报错，除非某个节点显式读取了缺失的键。
  • 在正式上线前，于预发布部署中使用时间旅行和 0，抽取已有线程对照新代码进行检查。

检测在途线程#

在你删除节点、重命名状态键，或进行其他旧线程无法容忍的变更之前，你会想知道当前是否有线程停留在你即将废弃的那个代码版本上。LangGraph 本身并不维护线程状态的搜索索引，因此答案取决于你的图运行在哪里。

如果你部署到 LangSmith。 使用 Agent Server 的线程搜索按状态过滤。status 字段接受 idle、busy、interrupted 和 error，因此你可以批量查询 interrupted 或 busy 的线程，还可以选择用元数据过滤进一步收窄范围。参见按线程状态过滤和列出线程。

无论 LangGraph 运行在哪里。 使用 LangSmith 追踪来监控生产环境中哪些节点正在被进入和退出。这是判断某个节点或状态字段是否已不再被任何活跃代码路径可达的最可靠信号。

当你已经有 thread_id 时。 直接检查该单个线程：

  • 0 返回最新的检查点，其中包括线程暂停在哪个节点，以及任何待处理的中断。
  • 0 返回该线程按时间顺序排列的完整检查点列表。

如有疑问，请保留已弃用的节点或字段，直到 Agent Server 的线程列表和追踪都显示它不再有任何活动。

业务兼容性#

有时某项变更在技术上是有效的（每个已有检查点仍能加载，每个节点仍能解析），但新图的*含义*与旧图不同。新行为对新线程来说是正确的，而你并不希望把它追溯应用到在旧逻辑下启动的线程。

例如，假设你的图执行 intake → triage → respond，而你决定在 triage 和 respond 之间插入一个新的 policy_check 步骤：

  • 已经通过 triage 的线程应当直接继续到 respond（旧流程）。
  • 新线程应当执行完整的新流程。

推荐的模式是在线程启动时把相关的*行为版本*记录到状态上，然后用条件边依据它进行分支：

python
from typing import NotRequired
from typing_extensions import TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    request: str
    flow_version: NotRequired[int]
    response: NotRequired[str]


def intake(state: State) -> dict:
    # Stamp new threads with the current flow version. Existing threads
    # that resume past `intake` keep whatever value was already saved.
    return {"flow_version": state.get("flow_version", 2)}


def triage(state: State) -> dict: ...
def policy_check(state: State) -> dict: ...
def respond(state: State) -> dict: ...


def after_triage(state: State) -> str:
    if state.get("flow_version", 1) >= 2:
        return "policy_check"
    return "respond"


builder = StateGraph(State)
builder.add_node("intake", intake)
builder.add_node("triage", triage)
builder.add_node("policy_check", policy_check)
builder.add_node("respond", respond)
builder.add_edge(START, "intake")
builder.add_edge("intake", "triage")
builder.add_conditional_edges("triage", after_triage, ["policy_check", "respond"])
builder.add_edge("policy_check", "respond")
builder.add_edge("respond", END)

graph = builder.compile()

在 triage 之后恢复的旧线程会从其已保存的状态中读取 flow_version（或回落到 v1 的默认值），从而跳过 policy_check。新线程从 intake 开始，被打上 flow_version=2 的标记，并执行新路径。等所有 v1 线程都完成后，你就可以移除版本标记和条件边。

这个模式只有在*线程启动时*就设置版本、且早于任何需要区分版本的支路时才有效。之后再设置意味着已有线程在需要该值时并没有设置它。

非确定性#

这一类问题仅适用于 Functional API，以及 Graph API 节点内部的 任务 或 0 调用。普通的 Graph API 节点在恢复时会从节点函数的开头重新运行；应把副作用设计为幂等的，但除非你在该节点中使用了任务或 1，否则无需保持任务调用顺序。

Functional API 的入口点会编译为单个节点，当运行恢复时，该节点会从头重放入口点主体，并利用缓存的 0 结果跳过已经完成的工作。有两类变更会破坏这一模型：

  • 新增、删除或重新排序位于恢复点*之前*的 @task 调用或 1 调用。LangGraph 依据调用在重放中的位置来匹配缓存结果和恢复值，因此位置发生偏移可能导致错误的缓存值被重放到另一个调用上。
  • 在 @task 之外引入非确定性操作，例如 time.time()、random.random()，或内联在入口点主体中的网络调用。重放时它们产生的值与首次运行不同，可能改变控制流。

如需带示例的深入讲解，请参阅 Functional API 指南中的确定性和常见陷阱。

如果你需要对存在进行中运行的 @entrypoint 做出并非微不足道的代码变更，最安全的选项是：

  • 在进行中的运行全部结束之后，再部署该变更。
  • 将任何新增逻辑包装到新的 @task 中，使其结果被独立地写入检查点。
  • 在 langgraph.json 中以新的图名称注册新的入口点以实现新行为，并将新线程路由到该入口点。
